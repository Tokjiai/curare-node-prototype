# サロン予約管理システム Node.jsプロトタイプ

## これは何か

現在GAS（Google Apps Script）＋Googleスプレッドシート＋LINEで動いている
サロン予約管理システムのうち、**予約エンジンのコア判定ロジック**（空き状況判定：
TEL / ー / 店休 / 満 / 残1 / 空き）を、**Node.js（Express）＋ SQLite** で
忠実に移植し、実際に動くことを確認したプロトタイプです。

> **⚠️ これは本番運用システムではありません。**
> 実際の店舗運営（LINE連携・顧客管理・スタッフダッシュボード等）は今回の対象外です。
> 本番は別途、**レンタルサーバー（VPS）＋ Node.js ＋ MySQL** で構築する計画です。
> このプロトタイプの目的は「予約エンジンのコアロジックが、GASを離れてNode.js側でも
> 正しく動くこと」を証明する点にあります。

### 今回あえて対象外にしたもの
- LINE通知（予約確定メッセージ送信、リマインダー等）
- Googleカレンダー連携（`COL_Y_SYNC` の同期処理）
- 顧客マスタとの統合（顧客ID・LINE友だち情報の紐付け）
- スタッフ向けダッシュボード・オーナー向け管理画面
- キャンセル待ち・仮予約フローの詳細

これらは「予約エンジンのコアロジック実証」というプロトタイプの目的から外れるため割愛しています。

## 3. ローカルでの動かし方

```bash
cd node-prototype
npm install
npm start
# → 🚀 予約管理プロトタイプ サーバー起動: http://localhost:3000
```

ブラウザで `http://localhost:3000` を開くと、
担当スタッフ・日付・時間帯・時刻を選んで予約できる簡易画面が表示されます。

サーバー起動時に毎回、`db/init.js` がSQLiteのテーブルを作り直し、
「クラーレ寿」を模したダミーデータ（店舗1つ・スタッフ3名・14日分のシフト・
既存予約数件・臨時休業日1件）を自動投入します。シードだけ再投入したい場合は
`npm run seed` でも実行できます。

## 4. Renderへのデプロイ手順（ユーザーご自身で行う部分）

このエージェントの実行環境からは実際のGitHub連携・Renderへのデプロイ操作は
行えないため、**準備まで**を整えてあります。以下の手順をコピペで進めてください。

### 手順1：GitHubリポジトリを作る

```bash
cd node-prototype
git init
git add .
git commit -m "予約エンジン Node.jsプロトタイプ 初回コミット"
```

GitHub上で新規リポジトリ（例：`salon-booking-prototype`）を作成し、
表示される案内に従ってpushしてください。

```bash
git remote add origin https://github.com/<あなたのユーザー名>/salon-booking-prototype.git
git branch -M main
git push -u origin main
```

### 手順2：Renderでサービスを作る

1. https://dashboard.render.com/ にログイン（GitHubアカウントでログイン可能）
2. 画面右上の **New +** → **Blueprint** を選択
3. 先ほどpushしたリポジトリを選択
4. リポジトリ内の `render.yaml` が自動検出され、
   「salon-booking-prototype」という名前のWebサービス（Freeプラン）が
   作成されることを確認
5. **Apply** をクリックしてデプロイを開始

### 手順3：デプロイ完了後の確認

- ビルドログで `npm install` → `npm start` が成功していることを確認
- 発行されたURL（例：`https://salon-booking-prototype.onrender.com`）に
  アクセスし、予約画面が表示されればOK

### 補足：無料プランの制約について

- Render無料プランのディスクは**エフェメラル**（再デプロイ・再起動のたびに消える）ため、
  本アプリはサーバー起動時に毎回SQLiteを初期化＋シードデータを再投入する設計にしてあります。
  → デプロイ後にAPIで登録したデータも、次回の再起動（無料プランは一定時間アクセスがないと
  スリープし、次のアクセスで再起動されます）で消える点はご承知おきください。
  プロトタイプとしての動作確認が目的なので、この割り切りで問題ありません。
- 無料プランはアクセスが一定時間ないとスリープするため、初回アクセス時は
  起動に数十秒かかることがあります。

## 5. 顧客マスタ・CSV取込・オーナー管理画面（追加機能）

このプロトタイプにはその後、以下の3つを追加しています。

### 5-1. 顧客マスタ（customers テーブル）

GASの「顧客マスタ」シートに相当するテーブルを `db/schema.sql` に追加しました。
`store_id` でスコープされ、`(store_id, customer_id)` に一意制約とインデックス、
`(store_id, realname)` にもインデックスを張っています。

主なカラム：`customer_id`（シート発行の顧客ID）, `realname`, `kana`, `phone`,
`line_name`, `user_id`（LINE userId）, `birthday`, `first_visit_date`,
`last_visit_date`, `total_visits`, `memo`。

`npm run seed`（＝`node db/init.js`）実行時にダミー顧客5名が自動投入されます。

### 5-2. CSV取込スクリプト（import_csv.js）

GASスプレッドシートをCSVエクスポートしたものを定期的に取り込むためのスクリプトです。
**GASが引き続き本番として稼働している間、並行運用でこのスクリプトを定期実行する**
ことを想定しています。実行するたびに同じ行は上書き更新されるだけなので、
**何度実行しても重複登録されません（冪等）**。

```bash
# 顧客マスタの取込
node import_csv.js customers ./顧客マスタ.csv --store=1

# 予約データの取込
node import_csv.js reservations ./予約データ.csv --store=1
```

- `--store=<slugまたはstore_id>` は省略可（省略時は store_id=1）。
- 顧客マスタは `store_id + customer_id` の一致で upsert。
- 予約データは `store_id + 担当 + 予約日 + 予約時刻` の一致で upsert
  （キャンセル済み予約は一意制約の対象外のため上書きされません）。
- 実行結果として「読み込み行数／新規登録／更新／スキップ（理由付き）」を表示します。

**列マッピングについて（★重要）**：実際のスプレッドシート側の列見出しや列順が
将来少し変わっても、直す場所を1箇所に集約するため、`import_csv.js` 冒頭の
`CUSTOMER_COLUMN_MAP` / `RESERVATION_COLUMN_MAP` というオブジェクトだけが
「CSVの列見出し（日本語）→ DBカラム名」の対応関係を持っています。
シート側の見出し表記が変わった場合は、この2つのオブジェクトのキー（左辺）を
直すだけで済み、パース処理・upsert処理のコードには手を入れる必要がありません。

顧客マスタCSVのヘッダー行の例（`CUSTOMER_COLUMN_MAP` のキーと一致させる）：

```
顧客ID,氏名,フリガナ,電話番号,LINE名,LINE userId,生年月日,初回来店日,最終来店日,来店回数,メモ
C0001,山田 花子,ヤマダ ハナコ,090-1234-5678,はなちゃん,U1234567890,1992-05-10,2025-01-10,2026-09-01,8,常連
```

予約データCSVのヘッダー行の例（`RESERVATION_COLUMN_MAP` のキーと一致させる）：

```
氏名,フリガナ,LINE名,LINE userId,担当,メニュー,予約日,予約時刻,備考,登録者,顧客ID,ステータス
山田 花子,ヤマダ ハナコ,はなちゃん,U1234567890,花子,フェイシャル(60分),2026-09-30,10:00,,寿子,C0001,確定
```

CSVパーサーは外部ライブラリを使わず自前実装（RFC4180相当のダブルクォート
エスケープに対応、UTF-8日本語もそのまま扱えます）なので、**依存パッケージの
追加はありません**。

### 5-3. オーナー用管理画面（/admin/*）

3つのAPIエンドポイントと、3つの管理画面ページを追加しました。

**APIエンドポイント（すべてログインセッション＋オーナー権限が必要）**

| メソッド・パス | 内容 |
|---|---|
| `GET /api/admin/customers?q=&limit=&offset=` | 顧客マスタの検索（氏名／フリガナ／電話番号の部分一致）、ページング対応 |
| `GET /api/admin/reservations?from=&to=&staffName=&q=&limit=&offset=` | 予約データの検索（日付範囲・担当・氏名部分一致）、新しい日付順、ページング対応 |
| `GET /api/admin/dashboard` | 本日/今週の予約件数、直近7日間の日別件数、総顧客数、累計予約件数（キャンセル除く） |

いずれも店舗は**ログイン中のセッションの店舗に固定**され、`?store=` を渡しても
無視されます（複数店舗展開時に他店のデータを覗けてしまう事故を防ぐため）。

**管理画面ページ（`public/admin/` 配下、単一HTMLファイルでCSS/JSともにインライン）**

| ページ | 内容 |
|---|---|
| `public/admin/login.html` | ログイン画面（店舗＋4桁PIN） |
| `public/admin/index.html` | ダッシュボード（本日/今週の件数、直近7日間の予約数リスト） |
| `public/admin/customers.html` | 顧客マスタ閲覧（検索ボックス＋一覧テーブル） |
| `public/admin/reservations.html` | 予約データ閲覧（日付範囲・担当フィルタ＋一覧テーブル） |

各ページはロード時に `GET /api/auth/me` を呼び、401ならログイン画面へリダイレクトします。
ナビゲーションに「ログアウト」リンクがあり、クリックで `POST /api/auth/logout` を呼んでからログイン画面へ戻ります。

## 6. ログイン機構（PINベース・セッション認証）

以前の「共有パスワード＋`X-Admin-Password`ヘッダー」方式は廃止し、
**GAS版の実運用と同じ「スタッフの電話番号下4桁PIN」によるログイン**に置き換えました。

### 6-1. ログインフロー

1. `public/admin/login.html` で店舗（slugまたはID）と4桁PINを入力
2. `POST /api/auth/login`（body: `{ store, pin }`）にリクエスト
   - サーバーは対象店舗の `staff` テーブルから候補を取得し、各候補の `pin_salt` で
     入力PINをハッシュ化して `pin_hash` と定数時間比較（`crypto.timingSafeEqual`）
   - 一致かつ `is_owner=1` のスタッフのみログイン成功
   - 一致したが `is_owner=0`（一般スタッフ）の場合は
     `{success:false, message:'現在はオーナー権限のみログインできます（プロトタイプ版）'}`
     を返す（＝将来一般スタッフ向け機能を実装する際にここを外すだけで済むように、
     「扉は開けたまま」明示的にブロックしている）
   - 一致しない場合は汎用的な `401 {success:false, message:'PINが正しくありません'}`
     （店舗が違うのかPINが違うのか等、攻撃の手がかりになる情報は返さない）
3. 成功時は `req.session.staff = {id, storeId, name, isOwner}` をセッションに保存し、
   `Set-Cookie` でセッションCookie（`httpOnly`）を返す
4. 以降、管理画面の各ページ・APIはこのセッションCookieで認証される
   （`credentials`指定は不要。ブラウザのfetchはデフォルトで同一オリジンCookieを送信する）

### 6-2. 開発用オーナーPINの確認方法

サーバー起動時（`node db/init.js` 実行時含む）のコンソールログに、
以下のような行が出力されます。これでログインできます。

```
🔑 [開発用] オーナーPIN: 5678 (store=1, staff=寿子) ※本番ではこの行は出力しないこと
```

現在のシード値は、寿子（オーナー）の電話番号下4桁 `5678`（store=1）です。
花子・美咲は一般スタッフとしてPIN付きで登録されていますが、
現段階では `is_owner=0` のためログインは拒否されます（403相当のメッセージ）。

### 6-3. `stores.plan` 列について（プレースホルダー）

`stores` テーブルに `plan VARCHAR(20) NOT NULL DEFAULT 'trial'` を追加しました。
将来の料金プラン（ワンコイン＝`onecoin` / ベース＝`base` / LINE連携＝`line`）に
対応するための置き場所で、**現時点ではどの機能もこの値を見て制御していません**。
将来「このプランならこの機能を使える／使えない」という判定を追加する際の
土台として、スキーマだけ先に用意してあります。

### 6-4. 本番化する際の注意（★重要）

このログイン機構は「実運用に耐えるコア設計」を意識して作っていますが、
以下は明示的にプロトタイプの範囲内であり、本番投入前に必ず対応してください。

- **セッションストアの差し替え**：現在は `express-session` のデフォルト
  `MemoryStore`（プロセス内メモリ）を使用しています。単一インスタンスの
  プロトタイプでは動作しますが、本番はプロセス再起動でセッションが消える／
  複数インスタンス間でセッションを共有できないため、`connect-mysql2` 等の
  永続化されたセッションストアに置き換える必要があります。
- **`SESSION_SECRET` の環境変数設定必須**：未設定時は開発用の固定値
  （`dev-only-insecure-session-secret`）を使い、起動時に警告を出力します。
  本番では必ず十分にランダムな値を環境変数で設定してください。
- **ログイン試行のレート制限**：4桁PINは総当たりが容易な情報量（1万通り）
  のため、現状は試行回数の制限を一切行っていません。本番では
  IPアドレス単位・店舗単位でのレート制限、一定回数失敗した場合の
  ロックアウト等を追加してください。
- **HTTPS必須化**：現在のCookie設定は `httpOnly: true` のみで
  `secure: true` を付けていません（ローカル開発でHTTPのまま動作確認するため）。
  本番はHTTPS環境になるため、`secure: true` を有効にし、Cookieが平文HTTP経由で
  漏れないようにしてください。
- 上記に加え、[6-2](#6-2-開発用オーナーpinの確認方法)のコンソールPIN出力は
  開発用の利便性のためのものです。本番ビルドではこの出力を無効化するか、
  ログ収集基盤に残らないようにする配慮が必要です。

## 7. 本番（VPS＋MySQL）移行時に注意すべき点

- **DB接続層の差し替え**：`lib/db.js` を `mysql2` 等に置き換え、
  `lib/reservationEngine.js` 内の `db.prepare(...).get()/.all()` の呼び出し方を
  MySQLクライアントのAPIに合わせて調整してください（SQL文自体は
  `schema.sql` を標準的な記法にしてあるので大きな変更は不要な想定です）。
- **AUTO_INCREMENT構文の違い**：SQLiteの `INTEGER PRIMARY KEY AUTOINCREMENT` は
  MySQLでは `INT PRIMARY KEY AUTO_INCREMENT` に読み替えてください（`schema.sql` に
  コメントで明記しています）。
- **日付・時刻の型**：今回は移植の忠実性を優先し、GAS版同様に文字列
  （`'YYYY-MM-DD'` / `'HH:MM'`）で保持・比較しています。本番でMySQLの
  `DATE`/`TIME`型・タイムゾーンを正しく使う設計に見直すことを推奨します。
- **同時実行制御**：GAS版は `withStoreLock_`（スプレッドシートロック）で
  予約登録の排他制御をしていました。本番のMySQLではトランザクション＋
  行ロック（`SELECT ... FOR UPDATE`）等での排他制御の実装が必要です。
- **未移植の機能**：カレンダー同期・各種ダッシュボードの拡充は、
  本番構築時にあらためて設計・実装が必要です（LINE連携は below の
  セクション8を参照。骨組みまで実装済みです）。

## 8. LINE連携（Messaging API）※このラウンドで追加・骨組みです

今回追加したLINE連携は、**「本番のLINE公式アカウントを持っていない今の段階でも
動かせる／構造は正しく作ってあり、環境変数を設定するだけで実運用に切り替えられる」**
という方針で実装した「骨組み（スキャフォールディング）」です。実際のLINEチャネル
に対しては未検証です。

### 8-1. Webhook（`POST /webhook/line`）

- ファイル：`routes/lineWebhook.js`（署名検証・イベント処理）、
  `lib/lineClient.js`（署名検証・プッシュ送信の共通ロジック）。
- 環境変数 `LINE_CHANNEL_SECRET`：LINE Developersコンソールで発行される
  チャネルシークレット。署名検証に使います。
  - **未設定の場合**：署名検証を行わず、リクエストごとに
    `⚠️ LINE_CHANNEL_SECRET未設定のため署名検証をスキップしました（開発用）`
    という警告をログに出したうえで、イベントの受信・パースは行います
    （200 OKを返します）。「検証したことにする」ことは絶対にしません。
  - **設定済みの場合**：`x-line-signature` ヘッダーの値をNode標準の
    `crypto`（HMAC-SHA256＋`crypto.timingSafeEqual`）で検証し、
    一致しなければ401で拒否します。
- 受信した各イベントは `📩 LINE Webhookイベント受信: type=... userId=... text=...`
  という1行ログで内容を確認できます（実際のビジネスロジックはまだ多くを
  実装していません。イベントが正しく届き、正しくパースできることの確認用です）。
- LINEの仕様上、Webhookは高速に200を返す必要があるため、内部処理で
  何が起きても（署名検証失敗を除き）最終的には200を返します。

### 8-2. スタッフPIN自動登録（実際に動作する唯一のビジネスロジック）

GAS版の実運用ドキュメントに基づく仕様：スタッフ向けLINE公式アカウントに
自分のログインPIN（4桁）をテキストで送ると、システムが自動的にそのLINE userId
を該当スタッフに登録します。

- テキストメッセージがちょうど4桁の数字のとき、`staff` テーブルの
  `pin_hash`（`lib/auth.js` の `verifyPin` で照合）と一致するスタッフを探します。
- 一致するスタッフの `staff.line_user_id` が空であれば、その場で自動登録し、
  成功ログを出します。
- 既に登録済みなら**上書きしません**（`既に登録済みです` とログを出すのみ）。
- 一致するスタッフが見つからない場合は**何もしません**（返信もしません。
  総当たりでPINを探索されても外部から「当たり／外れ」が分からないようにするため）。
- どの店舗のスタッフを探すかは、Webhook検証に使ったチャネルシークレットで
  `stores.line_staff_channel_secret` を照合して決めます（複数店舗展開時、
  店舗ごとに異なるLINEチャネルを割り当てる設計）。一致する店舗が無い場合は
  最初の店舗にフォールバックします（現状はプロトタイプが単一店舗のため）。

### 8-3. お客様への予約確定プッシュ通知

- ファイル：`lib/reservationNotify.js`（メッセージ組み立て）、
  `lib/lineClient.js` の `pushMessage`（実際の送信）。
- `POST /api/reservations` が成功すると、`customerId` が指定されていれば
  顧客マスタ（`customers.user_id` 列＝LINE userId。今回の追加にあたり新規の列は
  作らず、既存のこの列をそのまま通知先として使っています）を引いて通知を試みます。
- **顧客がLINE未連携（`user_id` が空）の場合**：送信せず、スキップのログを
  1行出すだけです（LINEを使っていないお客様も普通にいるため、これは
  異常系ではなく正常な分岐です）。
- **店舗の `stores.line_customer_channel_token` が未設定の場合（今の状態）**：
  実際には送信せず、`📱 [開発用/LINE未設定] 本来なら <userId> 宛にLINE通知: <本文>`
  というログを出す「シミュレーション」動作になります。
- **`stores.line_customer_channel_token` を設定すると**：LINEのプッシュメッセージ
  API（`https://api.line.me/v2/bot/message/push`）へNode 18+ の標準`fetch`で
  実際にPOSTします（`node-fetch`等の追加npm依存は不要。`package.json` の
  `engines.node` が `>=18.0.0` であることを前提にしています）。送信失敗時は
  エラー内容をログに出し、**予約登録のレスポンス自体は失敗させません**
  （LINE側の障害・未設定が予約そのものの成功を妨げないための設計。
  `server.js` の `POST /api/reservations` 内・`lib/reservationNotify.js` に
  同じ趣旨のコメントを明記しています）。

### 8-4. LINE関連の新規スキーマ列

- `staff.line_user_id`：スタッフ本人のLINE userId（8-2で自動登録）。
- `stores.line_customer_channel_token` / `stores.line_staff_channel_secret`：
  店舗ごとのLINEチャネル資格情報。**環境変数ではなくDBのこの列に持たせている
  理由**は、将来複数のサロンがそれぞれ自分のLINE公式アカウントを持つ
  マルチテナント運用になったとき、店舗ごとに異なる値をリクエスト時に
  読み出す必要があるためです（単一プロセスの環境変数では店舗をまたいで
  使い分けられません）。一方 `LINE_CHANNEL_SECRET` 環境変数は、この
  プロトタイプ自体の `/webhook/line` エンドポイントの署名検証専用で、役割が
  異なります。
- どちらもnullable・デフォルト値なしのプレースホルダーです。

### 8-5. これは骨組みです（できていないこと一覧）

## 9. Renderへの実データ投入手順

このリポジトリには `sample_data/customers.csv` と `sample_data/reservations.csv` を
同梱しています。実際の「テストB店」スプレッドシート（curare-storeB-db_TEST。
オーナー確認済みのテスト用ダミーデータで、本番のお客様情報ではありません）から
書き出したCSVで、ローカルでは `import_csv.js` による取込・動作確認を済ませています。
Renderにデプロイしたあと、同じデータをそのまま投入することができます。

### 9-1. 投入手順（★2026-09-18訂正：ボタン方式に変更）

当初はRenderの「Shell」タブから `node import_csv.js ...` を直接実行する手順を想定していましたが、
**Renderの無料（Free）プランにはShell機能が無い**ことが実機確認で判明したため、
Shellを使わない方式に変更しました。

1. 管理画面（`/admin/`）にオーナーPINでログインする。
2. ダッシュボード画面の「**テストB店データの取込（PROTOTYPE専用）**」パネルにある
   「**サンプルデータを取り込む**」ボタンを押す。
3. `POST /api/admin/import-sample-data`（server.js）が、`import_csv.js` の
   `importCustomers` / `importReservations` 関数をそのままサーバー内部で呼び出し、
   同梱の `sample_data/customers.csv` ・ `sample_data/reservations.csv` を取り込む。
   コマンドラインもShellアクセスも不要。
4. 画面上に「読み込み行数／新規登録／更新／スキップ」のサマリーが表示されれば投入完了です。

コマンドラインから直接実行したい場合（ローカル環境やShellが使えるホスティング先）は、
従来どおり以下のコマンドも使えます（`import_csv.js` 自体は変更していません）。

```bash
node import_csv.js customers sample_data/customers.csv --store=1
node import_csv.js reservations sample_data/reservations.csv --store=1
```

### 9-2. 【★重要】投入後は必ず `SKIP_SEED=1` を設定すること

上記の手順だけでは、**次にサーバーが再起動した瞬間に投入したデータが消えてしまいます。**
理由は次のとおりです。

- Renderの無料プランのディスクは**エフェメラル**（再起動・再デプロイのたびに中身が消える）です。
- このアプリはサーバー起動のたびに `db/init.js` を実行し、SQLiteのテーブルを作り直して
  「クラーレ寿」を模したダミーデータ（顧客5名など）を毎回自動投入する設計になっています
  （[3章](#3-ローカルでの動かし方)参照）。
- つまり、Shellで実データを投入した直後は見た目上うまくいっていても、無料プランは
  一定時間アクセスがないとスリープし、次のアクセスで再起動がかかるため、**そのタイミングで
  DBが初期化され、投入した実データが消えてダミーデータ5名に戻ってしまいます。**

これを防ぐには、Renderの **「Environment」** 設定画面（サービスの左サイドバー）で
環境変数を1つ追加してください。

| キー | 値 |
|---|---|
| `SKIP_SEED` | `1` |

追加したら、**「Manual Deploy」** から手動で再デプロイ（Redeploy）を1回実行してください。
`SKIP_SEED=1` が設定された状態で起動すると、`db/init.js` はテーブル作成・ダミーデータ投入を
スキップし、既存のSQLiteファイルをそのまま使うようになります。これで、Shellから投入した
実データが再起動後も保持されるようになります。

> **手順の順番に注意**：`SKIP_SEED=1` を設定してから実データを投入しても、その時点では
> まだテーブルが空（ダミーデータも実データも入っていない）の可能性があります。
> 「9-1でデータ投入 → 9-2で `SKIP_SEED=1` を設定して再デプロイ」の順番で進めてください。

### 9-3. 既知の制約：キャンセル済み予約の重複について

`sample_data/reservations.csv` を**複数回**インポートすると、キャンセル済みの予約
（`本名` が「キャンセル」になっている行）が重複して登録されることがあります。

原因は、予約データのupsert判定キー（`store_id + 担当 + 予約日 + 予約時刻`）が
キャンセル済み行には適用されない仕様になっている点にあります（[5-2章](#5-2-csv取込スクリプトimport_csvjs)
参照）。これは、キャンセル済み予約は元のスプレッドシート側の運用でも顧客IDが
空欄になっていることが多く、他の行と衝突しない一意なキーを持たせられないという
**元データ側（スプレッドシートのキャンセル運用の慣習）の制約**であり、
`import_csv.js` 自体のバグではありません。

そのため、**同じCSVスナップショットに対しては1回だけ実行する**のが推奨運用です。
最新のスプレッドシートを都度エクスポートして取り込む通常運用（[5-2章](#5-2-csv取込スクリプトimport_csvjs)）
であれば、キャンセル済み行が毎回同じ内容で複数回インポートされる状況は基本的に発生しません。

## 12. スタッフのシフト管理・予約の編集/キャンセル（2026-09-19追加）

社長からの指示（GAS版と機能面で同等になるよう優先し、課金機能の作り込みは
GAS移植が終わってから、という方針）に沿って、GAS版で稼働している以下2機能を追加しました。

### 12-1. スタッフのシフト管理（`/admin/shifts.html`）

オーナー管理画面に「🗓️ シフト管理」を追加。週単位のカレンダー形式で、日付ごとに
スタッフの出勤シフト（`shift_master`テーブル）を確認・追加・削除できます。GAS版の
スタッフダッシュボードにあるシフト編集モーダル（日付・スタッフ・開始時間・終了時間）の
操作感を踏襲しつつ、見た目はこのプロトタイプの管理画面共通デザイン（クリーム＋セージ配色）に
合わせています。

API：
- `GET /api/admin/staff` — シフト割当用の全スタッフ一覧（見習い・非表示スタッフも含む）
- `GET /api/admin/shifts?from=&to=` — 期間指定でシフト一覧を取得
- `POST /api/admin/shifts` — シフトを1件追加（終了時刻が開始時刻以前、または在籍していない
  スタッフ名の場合は400エラー）
- `DELETE /api/admin/shifts/:id` — シフトを1件削除（他店舗のIDを指定した場合は404）

### 12-2. 予約の編集・キャンセル（管理画面から操作）

`/admin/reservations.html` の一覧に「編集」「キャンセル」ボタンを追加しました。

- **編集**：担当・メニュー・日付・時刻・備考を変更できます。変更後の日時・担当が
  既に別の予約で埋まっている場合は、予約作成時と同じUNIQUE制約チェックで守られ、
  「その日時・担当は既に別の予約で埋まっています」というエラーになります
  （二重予約防止の仕組みを編集時にも使い回している）。
- **キャンセル**：GAS版の運用を踏襲し、物理削除ではなく`realname`列に'キャンセル'を
  入れる形で記録を残します。

**【重要・セキュリティ修正】** 旧実装の`DELETE /api/reservations/:id`はログインセッションの
確認も店舗スコープの確認も無い公開エンドポイントでした（フロント側では未使用だったため
実害はありませんでしたが、放置すべきではない不備でした）。今回、これを
`DELETE /api/admin/reservations/:id`・`PUT /api/admin/reservations/:id`として
`requireOwnerSession`必須・店舗スコープ確認付きに作り直しました。他店舗の予約IDを

## 14. 顧客マスタの重複統合（マージ）機能（2026-09-19追加）

GAS版の`customer_merge_functions.gs`に相当する、顧客マスタの重複検知・統合機能を追加しました。
長年の運用で電話番号を変えずに何度か登録し直してしまった、といったケースで、同一人物が
別々の顧客IDで重複登録されてしまう問題に対応します。

### 14-1. GAS版との違い（設計上の割り切り）

GAS版は、LINE Webhook・お客様予約フォーム・スタッフ手入力など「顧客が新規作成される
複数の入口」それぞれで自動的に重複を検知していました。このNode試作版では、現時点で
顧客が作成される経路がCSV取込（GAS側で発行済みの顧客IDをそのまま引き継ぐ）のみのため、
「作成時に自動検知する」のではなく「電話番号が一致する現行データをいつでもスキャンできる」
方式に置き換えています。統合・見送りの結果を記録する仕組みはGAS版と同じ考え方です。

### 14-2. 画面（`/admin/customers.html`）

顧客マスタ画面の上部に「⚠️ 重複の可能性がある顧客」パネルが表示されます（該当が無い時は
非表示）。電話番号が一致するのに顧客IDが異なる組み合わせを一覧表示し、それぞれに対して

- **統合する**：どちらを残すか選び、実行すると片方の空欄をもう片方の情報で埋めた上で、
  もう片方は削除済み扱い（論理削除）になります。来店回数は合算されます
- **別人として見送る**：同一人物ではないと判断した場合。両方の顧客データはそのまま残り、
  以後この組み合わせは重複候補として二度と表示されません

### 14-3. API（`server.js` / `lib/customerMerge.js`）

- `GET /api/admin/customers/merge-candidates` — 重複候補一覧（見送り済みは除外）
- `POST /api/admin/customers/merge-candidates/dismiss` — `{ customerIdA, customerIdB }` で見送りを記録
- `POST /api/admin/customers/merge` — `{ keepCustomerId, mergeCustomerId }` で統合を実行
  （店舗スコープ確認あり。他店舗の顧客IDを指定すると400エラー）
- `GET /api/admin/customers`（既存）は`is_deleted = 0`の絞り込みを追加し、統合で削除済みに
  なった顧客が一覧に出てこないようにしました

DBには`customers.is_deleted`／`customers.deleted_at`（論理削除用）と、見送り記録を保存する
`customer_merge_dismissals`テーブルを追加しています。

`scripts/integration_test.js`に、重複候補の検出・店舗スコープ確認・統合の実行（来店回数の

## 18. ログイン管理（強制ログアウト、2026-09-19追加）

GAS版owner_ui.htmlの「店舗設定」ハブに残っていたタイルのうち、

### 18-1. GAS版との違い（設計上の割り切り）

同時に持てて、ログアウト時はまとめて無効化する」という挙動は、Cookieセッションでも
自然に同じ形で再現できています（同じスタッフで複数端末からログインしていても、
強制ログアウトで全端末分が一括無効化されることを統合テストで確認済み）。

## 20. ログイン画面の使い勝手改善（2026-09-19追加・不具合修正）

社長より「サイドバーの顧客マスタを押しても使用者とPINの入力を求められる画面が現れて、
入力するとこれと同じ画面にループして戻ってくる」との報告があり、原因を調査・修正しました。

### 20-1. 原因

2つの問題が重なっていました。

1. **ログイン後に必ずダッシュボードへ戻る仕様だった**：セッション切れの状態で「顧客マスタ」
   （や他のどの管理画面）を開こうとすると、いったんログイン画面に飛ばされます。ここでPINを
   入力してログインに成功しても、これまでは必ず`/admin/index.html`（ダッシュボード）へ
   戻る実装になっていたため、「顧客マスタを開きたかったのに、また別の画面に飛ばされた」状態になり、
   目的の画面にたどり着くには手動でもう一度「顧客マスタ」を押し直す必要がありました
2. **店舗欄が毎回空欄だった**：ログイン画面には「店舗（slugまたはID）」と「PIN」の2つの入力欄が
   ありますが、店舗欄は毎回空のままでした。PINだけ入力して送信すると「店舗とPINを入力してください」
   というエラーで弾かれて同じ画面に留まり続けるため、店舗欄への入力を忘れていることに気づきにくく、
   「入力してもループする」ように見えていたと考えられます

### 20-2. 修正内容

- 全管理画面（ダッシュボード・顧客マスタ・予約データ・シフト管理・スタッフ管理・店舗設定）で、
  セッション切れによりログイン画面へ飛ばされる際に`?next=`パラメータで元のページを覚えておき、
  ログイン成功後はダッシュボードではなく元のページへ戻るように変更（`/admin/`配下のパス以外は
  許可しないオープンリダイレクト対策あり）
- ログイン画面（`/admin/login.html`）で、ログイン成功時にブラウザの`localStorage`へ店舗識別子を
  記憶し、次回アクセス時に自動入力するように変更。これにより通常の利用では店舗欄への入力が
  実質不要になり、PIN欄にフォーカスが当たった状態で開くようになります

これは新機能ではなく、既存のログイン導線が分かりにくかった点の使い勝手改善です。

## 21. ログイン画面：PIN入力中に数字が消える不具合の修正（2026-09-19追加・不具合修正）

v17の修正後、社長より「PINを入力しても文字がそばから消えていく」との報告があり、追加調査・修正しました。

### 21-1. 原因

ブラウザの開発者ツールで確認したところ、コンソールに
「Password field is not contained in a form」（パスワード欄が`<form>`要素の中に
入っていない）という警告が出ていました。以前の実装では、店舗欄・PIN欄・ログインボタンが
`<form>`で囲まれておらず、ただの`<input type="password">`として単独で置かれていました。
これが一部のブラウザ拡張機能（パスワード管理系など）の誤介入を招き、入力した数字が
そばから消えてしまう症状の原因だったと考えられます。

### 21-2. 修正内容

- 店舗欄・PIN欄・ログインボタンを正式な`<form>`要素で囲み、送信をsubmitイベントに
  一本化（Enterキーでの送信も自然に効くようになった）
- PIN欄の`type`を`password`から`text`に変更。GAS版と同様にこのPINは「スタッフの電話番号
  下4桁」という運用上の簡易な識別コードであり、銀行口座の暗証番号のような機密情報ではない
  ため、パスワードマネージャー系拡張機能に「パスワード欄」として認識・介入されるリスクを
  そもそも避ける方が安全と判断（見た目は引き続き文字間隔を広げて入力しやすくしている）
- 店舗欄・PIN欄の両方に`autocomplete="off"`と、主要なパスワードマネージャー拡張機能
  （LastPass・1Password等）向けの無視指定属性を追加

実際にヘッドレスブラウザで1文字ずつ入力するテストを行い、入力した数字が消えずに
「5678」のまま保持され、ログイン→目的のページへの遷移まで問題なく行われることを確認済みです。

## 22. ログイン画面：PINを入力してログインしても、また同じログイン画面に戻ってしまう不具合の修正（2026-09-19追加・不具合修正）

v21の修正後もなお「相変わらず顧客マスタに入れません」「PIN入力→ログイン後、また同じ
ログイン画面に戻る」との報告があり、追加調査・修正しました。

### 22-1. 原因（推定）

ローカル環境（curlによる再現テスト含む）ではログイン→セッション認証の一連の流れに問題は
見られませんでした。一方で本番はRenderの無料プランで動いており、TLSを終端するリバース
プロキシの背後でアプリが動作しています。この構成特有の既知の落とし穴として、以下の点が
「ログインは成功しているように見えるが、直後のページでセッションが認識されずログイン画面へ
送り返される」症状を引き起こしうることが分かりました。

- `app.set('trust proxy', ...)`を設定していなかったため、Expressがプロキシ経由のHTTPS接続を
  正しく認識できていなかった（`req.secure`が常にfalseになる）
- Cookieの`sameSite`属性を明示していなかった
- ログインAPI側で、セッションへの書き込み（`req.session.staff = ...`）を行った直後に
  `req.session.save()`の完了を待たずに`res.json()`でレスポンスを返していたため、環境に
  よってはセッションストアへの保存が完了する前にレスポンスが返り、直後のリクエストで
  セッションが見つからない可能性があった

原因を一つに断定できる決定的な証拠（本番サーバーのログ等）までは確認できていませんが、
上記はいずれもRenderのようなプロキシ環境で典型的に発生する不具合パターンであり、まとめて
対策しておくことで再発を防ぎます。

### 22-2. 修正内容

- `app.set('trust proxy', 1)`を追加し、Renderのプロキシ経由でもHTTPS接続を正しく認識できる
  ようにした
- セッションCookieに`sameSite: 'lax'`と`secure: 'auto'`を明示（本番のHTTPSでは自動的に
  Secure属性つき、ローカル開発のHTTPではSecure属性なしで動作する）
- ログインAPI（`POST /api/auth/login`）で、`req.session.save()`のコールバックを待ってから
  レスポンスを返すように変更し、「セッション保存前にレスポンスが返ってしまう」可能性を排除

### 22-3. 確認方法

ローカルでのcurlによる一連の流れ（ログイン→Cookie保持→`/api/auth/me`でセッション確認）は
引き続き正常に動作することを確認済みです。ただし本番のRender環境そのものにはこのサンドボックス
からアクセスできないため、実際にこの修正で症状が解消するかは、社長にデプロイ後の動作確認を
お願いする必要があります。もし本修正後もまだ症状が再現する場合は、ログイン直後のブラウザの
「開発者ツール → Application（アプリケーション）タブ → Cookies」で`connect.sid`という
Cookieが実際に保存されているかどうかのスクリーンショットをいただけると、原因をさらに
絞り込めます。

## 23. 顧客マスタに入れない不具合の本当の原因が判明・修正（2026-09-19追加・不具合修正）

v19デプロイ後も社長より「相変わらず顧客マスタに入れません」との報告があり、ブラウザの
開発者ツール「Network」タブで実際の通信を確認していただいたところ、v19までの調査は
的外れで、本当の原因は全く別のところにあることが判明しました。

### 23-1. 本当の原因

社長にいただいたNetworkタブのキャプチャにより、以下が判明しました。

- ログインAPI（`/api/auth/login`）は200（成功）
- 直後の顧客マスタ画面（`/admin/customers.html`）への遷移も正常
- ログイン状態の確認（`/api/auth/me`）も正常
- しかし、顧客一覧を取得するAPI（`/api/admin/customers?limit=50&offset=0`）が
  **500エラー**になっており、これが原因でJavaScript側が「セッション切れ」と
  誤判定し、ログイン画面へ送り返していた（＝ログインは実際には成功していたのに、
  顧客一覧の取得に失敗していただけだった）

コード側を調査した結果、根本原因は「DBのテーブル定義（schema.sql）に、このセッション中に
何度か新しい列（`is_deleted`・`status`・`staff_name`等）を追加してきたが、
`CREATE TABLE IF NOT EXISTS`は“テーブルがまだ無い場合”にしか効かないため、既に
customersテーブルが存在するDBファイル（本番でSKIP_SEED=1により保持されているデータ、
または過去バージョン時点のdata/app.dbファイル）には、その新しい列が自動的には
追加されていなかった」ことでした。その状態で新しいコードが`is_deleted`列などを
前提にSELECT文を実行すると、「no such column」エラーとなり500が返っていたと考えられます。

v15〜v19までの一連の調査（PIN欄の不具合修正・セッションCookie周りの対策）はいずれも
実際に存在した別の小さな問題点への対策としては無駄ではありませんでしたが、「顧客マスタに
入れない」という今回の症状そのものの直接の原因ではありませんでした。

### 23-2. 修正内容

- `lib/migrate.js`を新規作成。起動のたびに、実際のテーブルに存在する列と、
  現在のschema.sqlが期待する列を比較し、足りない列があれば
  `ALTER TABLE ... ADD COLUMN ...`で自動的に追加する、簡易マイグレーション処理を追加
- `db/init.js`（通常起動時）・`server.js`のSKIP_SEED=1分岐（データ保持起動時）の
  どちらの起動経路からも必ずこのマイグレーションを実行するように変更。これにより、
  今後同様にschema.sqlへ列を追加した際も、既存のDBファイルを持つ環境（本番含む）で
  自動的に追従され、同種の事故が再発しにくくなる
- 実際に「新しい列が無い旧スキーマのテーブル」を再現したテストで、マイグレーション後に
  正しく列が追加され、既存データ（顧客の氏名・電話番号等）を保持したまま顧客一覧の
  取得が成功することを確認済み

### 23-3. 教訓

この一連のやり取りでは、社長からログイン画面のスクリーンショットだけでなく、
「Networkタブ」「Keep log（ログを保持）」という具体的な操作をお願いして実際の通信内容を
見せていただいたことで、ようやく本当の原因（顧客一覧APIの500エラー）にたどり着けました。
見た目の症状（「ログイン画面に戻る」）だけでは、ログインそのものの不具合なのか、
ログイン後の別のAPIの不具合なのかを区別できないケースがある、という教訓を得ました。

### 30-1. 実装内容

  更新する。②完了（`done=1`）・有効な予約を`customer_id`ごとに数え、
  `customers.total_visits`を再集計する（現在の値より多い場合のみ更新。手動で入力した

### 30-2. GAS版からの意図的な簡略化

  別途スケジューラの導入（またはRenderのCron Jobs等のインフラ機能の利用）が必要
- GAS版は完了予約の集計をLINEのuserIdでしか顧客に紐付けられなかったが、Node版は予約

  結果としてLINE未連携の顧客も正しく集計対象に含まれるようになり、GAS版より対象が
  広がっている（改善的な差異）
- GAS版の③古いキャンセル予約の自動削除・④シフトの自動展開（曜日パターンからの
  自動生成）は、それぞれ別途の設計判断（削除基準日数の設定、シフトパターンの
  データモデル）が必要なため、今回は対象外とした（今後の拡張候補）

### 30-3. テスト・確認

- 統合テストに8項目追加し、計163項目（22カテゴリ）全パスを確認（過去日・顧客ID付きの
  予約が完了扱いに更新されること・来店回数が正しく増加すること・2回目の実行では対象が
  0件になる冪等性・手動で多めに設定した来店回数が減らされないこと・キャンセル済みの
  過去日予約は対象にならないこと）
- ヘッドレスブラウザで、オーナーとしてログイン→ダッシュボードの「日次メンテナンスを
  今すぐ実行」ボタンを押し、実行結果（①②の件数）がその場に表示されることを
  スクリーンショットで確認済み

## 31. LINE Webhookのfollow/スタンプ/キーワード返信（GAS版webhook_handler.gsの
    一部移植）（2026-09-21追加）

GASソース`webhook_handler.gs`（LINEの各種Webhookイベントを一括で受け取る`doPost`と、
そこから呼ばれる各イベントハンドラ群）を調査。`routes/lineWebhook.js`のファイル冒頭
コメントに「署名検証とスタッフPIN登録のみ実装、それ以外（友だち追加時の顧客登録・
あいさつ返信、スタンプへの定型返信、キーワードへの予約案内）は今回未実装」と明記
されていた既知のギャップを埋めた。

### 31-1. 実装内容

- `lib/customerMerge.js`に`findOrCreateCustomerFromLine(db, storeId, lineUserId, lineName)`
  を新規追加。LINEのuserIdで顧客マスタを検索し、未登録なら新しい顧客ID（`C0001`形式、
  店舗内の最大値+1）を自動採番して新規登録する。これまでNode版の顧客新規作成経路は
  CSV取込（顧客IDはGAS側で発行済み）のみだったため、**Node版自身が新しい顧客IDを
  発行して新規作成する初めての経路**になる。本名が未確定（LINEの表示名しか分からない）
  新規行は、一覧で見つけやすいよう`status='inactive'`（非アクティブ）分類にしておく
  （予約受付・LINE通知そのものには影響しない表示専用の区分）
- `lib/lineClient.js`に`replyMessage(channelAccessToken, replyToken, text, buttonUrl)`と
  `getLineDisplayName(channelAccessToken, userId)`を新規追加。`replyMessage`は
  `buttonUrl`を渡すと「本文＋『予約画面を開く』ボタン」のFlex Messageを組み立てる
  （GAS版`replyMessage_`と同等）。両関数とも、既存の`pushMessage`と同様にチャネル
  アクセストークン未設定時は実送信せずコンソールログのみの開発用シミュレーション
  動作になる
- `routes/lineWebhook.js`に3つのイベントハンドラを追加：
  - `handleFollow`：友だち追加イベントを受けて、LINE表示名を取得→顧客マスタへ
    自動登録→（LINE連携プランかつテンプレート設定済みの場合のみ）あいさつ
    メッセージを返信
  - `handleSticker`：スタンプ受信に対して「スタンプありがとうございます😊」の
    定型返信
  - `handleReservationKeyword`：テキストが「エステ予約したい」と完全一致した場合、
    予約画面（`PUBLIC_BASE_URL`環境変数から組み立て、顧客ID判明時は`cid`パラメータ
    付き）を案内する返信
  - Webhookのイベント処理ループを、DB書き込みを含む非同期処理を確実に待ってから
    HTTPレスポンスを返すよう`for...of`＋`await`の非同期ループに変更（従来の
    `forEach`のままだと、レスポンスがDB書き込み完了より先に返ってしまう可能性が
    あったため）

### 31-2. GAS版からの意図的な簡略化

- GAS版はLINE公式アカウントを「お客様向け（A）」「スタッフ向け（B）」の2系統持ち、
  Webhookの`destination`で送り分けていたが、このプロトタイプはまだ1系統の
  `/webhook/line`しか無いため、友だち追加・スタンプ・キーワード返信の処理は
  （スタッフPIN登録の処理と同様に）送信元を区別せず全イベントに対して動作する。
  実際のLINE公式アカウントを2系統接続する際は、`destination`ベースの振り分けを
  追加する必要がある（コード内にコメントで明記済み）
- GAS版は友だち追加時、LINE userIdの一致に加えて電話番号＋フリガナの一致でも
  既存顧客行への自動バックフィルを行っていたが、友だち追加の時点ではお客様の
  電話番号・フリガナが分からない（LINEの表示名しか取得できない）ため、この
  プロトタイプでは対象外とした。電話番号を伴う重複は、既存の`findMergeCandidates`
  （スキャン方式の重複検出、11章参照）が後からカバーする
- GAS版はあいさつメッセージの送信可否をコントラクト設定（`LINE_NOTIFY_OPTION_CONTRACT`）
  で判定していたが、Node版は既存の`hasFeature(plan, 'lineNotify')`（プラン機能制限、
  6章参照）で代替した。トライアル等のLINE連携対象外プランでは、顧客登録自体は
  行われるがあいさつ返信はスキップされる

### 31-3. テスト・確認

- 実際にLINE公式アカウントを接続していない開発環境でも動作確認できるよう、まず
  ローカルの開発サーバーに対してシミュレートしたWebhookペイロード（`follow`・
  `sticker`・`エステ予約したい`テキスト）を直接POSTする手動テストスクリプトで、
  顧客の自動登録（初回`isNew=true`・2回目以降`isNew=false`で冪等）、スタンプへの
  定型返信、キーワードへの予約リンク案内（`PUBLIC_BASE_URL`設定時はボタン付き・
  未設定時はテキストのみにフォールバック）、プランによるあいさつ返信のスキップ／
  送信の切り替えを、いずれもサーバーログで直接確認した
- 統合テストに8項目追加し、計172項目（23カテゴリ）全パスを確認（友だち追加での
  顧客自動登録・2回目の冪等性・スタンプ/キーワード/キーワード不一致それぞれの
  200応答・LINE連携プランでのあいさつメッセージ組み立て〜送信呼び出しの完走）

## 32. LINE連携設定パネル（チャネルアクセストークン／チャネルシークレットの
    入力画面）（2026-09-21追加）

31章でLINE Webhookのfollow/スタンプ/キーワード応答を実装した時点では、実際に
送受信で使う「チャネルアクセストークン」「チャネルシークレット」を設定する手段が
DBを直接書き換える以外に無かった（`stores.line_customer_channel_token` /
`stores.line_staff_channel_secret`列自体はv1から存在したが、入力するUIが未実装
だった）。実際のLINE公式アカウント（テストB店用「モデルB店公式」等）との接続に
向けて、管理画面から自己完結で設定できるようにした。

### 32-1. 実装内容

- 新規`GET/PUT /api/admin/settings/line`（オーナー専用・店舗スコープ）を実装。
  GETは値そのものを返さず、設定済みかどうかと末尾4文字のヒントのみを返す
  （管理画面に平文のトークンを表示し続けないため）。PUTは空欄の項目は
  「変更しない」として扱い、入力された項目のみを更新する
- `/admin/settings.html`（店舗設定）に「LINE連携設定」パネルを追加。チャネル
  アクセストークン・チャネルシークレットの入力欄と、LINE Developersコンソールの
  「Webhook URL」欄に設定すべきURL（`PUBLIC_BASE_URL`環境変数から自動組み立て）を
  表示する

### 32-2. GAS版からの意図的な簡略化・既知の制約

- Webhookの署名検証自体（`lib/lineClient.js`の`verifyLineSignature`）は、引き続き
  サーバー環境変数`LINE_CHANNEL_SECRET`（Renderのデプロイ環境変数設定）の1本構成の
  ままで、このパネルで入力した`stores.line_staff_channel_secret`列は単体では署名
  検証に使われない。現状は「LINEチャネル1つ＝運用中の店舗1つ」を前提にしており、
  複数店舗が同時に実LINE接続する段階になったら、`routes/lineWebhook.js`の
  `resolveStoreIdForWebhook`が参照するこの列を使った本格的な店舗判別ロジックに
  切り替える必要がある（コード内にコメントで明記済み）
- チャネルアクセストークンはDBに平文で保存する設計（既存の`line_customer_channel_token`
  列の設計を踏襲）。本番運用に向けては暗号化保存やアクセス権限の見直しが必要

### 32-3. テスト・確認

- 統合テストに10項目追加し、計182項目（24カテゴリ）全パスを確認（未ログイン時の
  401・初期状態が未設定として返ること・空欄保存の拒否・トークン/シークレットの
  個別保存と末尾4文字ヒントでの確認・他店舗オーナーの保存が自店に影響しないこと）
- 開発サーバーに対して実際にPIN認証でログイン→トークン保存→再取得の一連の流れを
  手動スクリプトで実行し、保存後の値が平文で返らずヒントのみになることを確認済み
